# Разрешения в веб-сессиях — один список на всю экосистему

> SSOT: `AI_OS/.claude/web-permissions.json`.

## Зачем

Без allowlist каждая рутинная операция — запрос к базе, коммит, публикация артефакта —
требует подтверждения вручную. Это рвёт работу и съедает время владельца.

## Где Claude Code вообще ищет разрешения

Здесь была дорого стоившая ошибка, поэтому по порядку.

Настройки проекта читаются из `<рабочая директория сессии>/.claude/settings.json`.
В веб-сессии рабочая директория — **`/home/user`**, и это не репозиторий: репозитории
лежат в нём подпапками.

Отсюда следствие, которое ломает интуицию:

> **`<репозиторий>/.claude/settings.json` в веб-сессии не читается вообще.**
> Ни в SellerBase, ни в любом другом. Он выглядит как настройки проекта, но проектом
> для сессии является `/home/user`.

Проверено на живом примере: в `SellerBase/.claude/settings.json` лежали 71 разрешение,
включая `mcp__Supabase__execute_sql` и `defaultMode: acceptEdits`, — и запрос к Supabase
всё равно спрашивал подтверждения.

Работающий адрес — **`$HOME/.claude/settings.json`**, где `HOME` равен `/root`.
Про это — следующий раздел, там вторая половина ошибки.

## Куда именно писать: HOME равен /root

Вторая половина той же ошибки, и без неё первая не лечится.

`HOME` в веб-контейнере — **`/root`**, а не `/home/user`. Пользовательские настройки
Claude Code читает из `$HOME/.claude/settings.json`, то есть из `/root/.claude/`.

Скрипт `setup_context_mode.sh` долгое время писал только в
`/home/user/.claude/settings.json`. Это настройки **уровня проекта** для корня сессии,
и разрешения на MCP-инструменты из них не применяются. Со стороны выглядело неотличимо
от «скрипт не запустился»: в логе сессии честное `Ran setup script`, а окно подтверждения
на `execute_sql` всё равно появлялось.

Скрипт теперь пишет **в оба места**: `$HOME/.claude/settings.json` — рабочий путь,
`/home/user/.claude/settings.json` — на случай, если корень сессии окажется другим.

## Проблема этого адреса

Контейнер эфемерный: `/home/user/.claude/settings.json` пересоздаётся при старте сессии.
Разрешения в него попадают только когда отрабатывает
`AI_OS/scripts/setup_context_mode.sh`, который вклеивает туда содержимое
`web-permissions.json`.

Пока скрипт запускается **вручную**, схема ненадёжна по построению: забыли команду —
сессия работает без разрешений, и окна возвращаются.

## Правильное решение: setup script окружения

Команду нужно перенести из ручного запуска в **setup script окружения** Claude Code
on the web. Тогда она выполняется до первого хода в каждой сессии, и вспоминать про неё
не приходится.

Настраивается в веб-интерфейсе, в параметрах окружения. Содержимое:

```bash
bash /home/user/AI_OS/scripts/setup_context_mode.sh
```

Документация по окружениям — https://code.claude.com/docs/en/claude-code-on-the-web

Скрипт ставит и хуки context-mode, и разрешения, поэтому одной строкой закрываются обе
задачи разом.

## Запасной путь: слово «настройся»

Пока setup script не настроен — или если он не сработал из-за порядка запуска — владелица
пишет в начале сессии одно слово:

> **настройся**

По нему ИИ **немедленно, без уточняющих вопросов** выполняет:

```bash
bash /home/user/AI_OS/scripts/setup_context_mode.sh
```

Одно подтверждение на запуск — и дальше сессия работает без окон. Помнить путь владелице
не нужно, только слово.

Это правило действует во всех репозиториях экосистемы. Слово может быть написано в любом
регистре и с опечатками — распознавать **семантически**, как и прочие триггеры.

## Что в списке

`defaultMode: auto` — режим, который документация описывает как «eliminate prompts
with auto mode»: решения принимает классификатор, а не окно подтверждения.

Раньше стояло `acceptEdits`, и это была ещё одна причина возвращавшихся окон:
`acceptEdits` пропускает без вопросов **только правки файлов**, а вызовы инструментов
подтверждаются всё равно — даже те, что перечислены в `allow`.

**Допустимые значения ровно четыре:** `plan`, `ask`, `auto`, `bypassPermissions`.
Значения `dontAsk` не существует — выдумывать его не надо, я на этом уже ошибся.
`bypassPermissions` пропускает вообще все проверки, включая список `deny`, поэтому
он нам не подходит.

**У `auto` есть условие: модель 4.6 или новее.** На Haiku 4.5 режим недоступен —
в переключателе режимов он серый с пометкой «Requires Claude 4.6 or newer», и сессия
откатывается на `acceptEdits` со всеми вопросами. То есть мало выставить режим,
сессия должна ещё идти на Opus 5 или Sonnet 5.

Проверяется по двум индикаторам в левом и правом нижнем углу сессии: там видно
применившийся режим и модель.

Список `deny` действует по-прежнему и остаётся ограничителем: расширять его надо
осознанно, а сокращать — нет.

Разрешено: чтение и поиск, `git` кроме опасного, `mcp__Supabase__*` (включая `execute_sql`,
`apply_migration`, `deploy_edge_function`), `mcp__github__*` для PR и чтения, инструменты
сессии (`Artifact`, `Skill`, `ToolSearch`, `SendUserFile`, `ReadNotifications`),
`mcp__Claude_Code_Remote__*` для триггеров и подписок на PR.

Запрещено всегда: `git push --force`, `git push -f`, `git push origin main`,
`git reset --hard`, `rm -rf`, `curl`, `wget`, `supabase secrets`, чтение `.env`.

## Правила ведения

1. Правится **только** `AI_OS/.claude/web-permissions.json`. Правка в
   `/home/user/.claude/settings.json` живёт до конца сессии и пропадёт.
2. Копии в репозиториях заводить не нужно: в веб-сессии они не читаются. Копия в
   `SellerBase/.claude/settings.json` осталась исторически — она безвредна, но ни на что
   не влияет, и полагаться на неё нельзя.
3. Новый инструмент, который просит подтверждения на рутинной операции, добавляется
   в список тем же PR, что и работа, где он понадобился.
4. Список запретов не расширяется «на всякий случай»: он про необратимое, а не про
   осторожность.
5. Изменения обязаны попасть в `main` AI_OS: скрипт читает файл с диска, а диск
   собирается из `main`.

## Чего этот список не отменяет

Прерывание — не отказ в разрешении. Если владелец пишет сообщение, пока идёт вызов
инструмента, вызов отменяется и выглядит как «Denied by user». Это не повод лезть
в allowlist.

## Окна на запросах к базе — это норма, а не поломка

**Решение владелицы от 2026-08-28: так и оставляем. Заново не расследовать.**

Настройка доведена до рабочего состояния: путь `$HOME`, режим `auto`, модель не ниже 4.6.
Проверено вживую — индикаторы сессии показывают «Auto» и «Sonnet 5». После этого окна
подтверждения исчезли почти везде, **кроме вызовов MCP-коннекторов** вроде
`Execute SQL (Supabase)`.

Это устройство площадки, а не наша недоработка:

- `auto` — режим **с классификатором**, а не «разрешить всё». Он пропускает то, что
  считает безопасным, и спрашивает на том, что считает рискованным. Запрос к боевой базе
  попадает во вторую категорию даже когда это `SELECT`.
- В самом окне варианты только «Allow once» и «Deny». Кнопки «разрешить всегда» нет —
  для коннекторов площадка её не предполагает. Наличие инструмента в `allow` этого
  не меняет.

Подтверждать удобно с клавиатуры: **Ctrl+Enter** — одно нажатие.

### Сводить запросы к базе в один вызов

Раз окно появляется на каждый вызов коннектора, число окон = число вызовов. Поэтому:

- Несколько независимых проверок — **одним** `execute_sql`, а не серией. Способы:
  `UNION ALL` с колонкой-меткой, несколько CTE в одном `SELECT`, или
  `SELECT json_build_object('a', (…), 'b', (…))`.
- Раздельно — только когда следующий запрос зависит от результата предыдущего.
- Чтение и запись не смешивать в одном вызове. Изменения структуры —
  по-прежнему отдельной миграцией через `apply_migration`.

Цель — одно окно на один смысловой шаг работы, а не на каждый вопрос к базе.

### Штатно окно не отключить — проверено 2026-09-24

Решение владелицы: убрать окно штатными средствами. Проверено, штатных средств нет:

- **Переключатель режима** в веб-сессии предлагает только `Auto`, `Accept edits`, `Plan`.
  `Bypass permissions` и `Don't ask` в облачных сессиях не показываются. `Auto` — уже
  самый свободный из доступных.
- **Страница коннектора** на claude.ai (`claude.ai/customize/connectors` → Supabase):
  список инструментов без переключателей, в меню «⋮» только `Disconnect`. Разрешений
  на отдельные инструменты там нет.
- **Настройки Supabase** окном Claude не управляют. Параметр `features=` в адресе
  коннектора убирает опасные инструменты (`pause_project`, `restore_project`,
  `create_project`, ветки), но окно на оставшихся не снимает. Адрес официального
  коннектора не редактируется — только через custom connector.

Остаются: Ctrl+Enter и сведение запросов в один вызов (раздел выше).

### Почему не `bypassPermissions`

Он убрал бы и эти окна, но вместе с ними — **весь список `deny`**: `rm -rf`,
`git push --force`, `git push origin main`, `git reset --hard`, `curl`, `wget`,
секреты Supabase, чтение `.env`. Размен признан невыгодным: защита от необратимого
дороже, чем несколько подтверждений в день.

### Что НЕ нужно делать при виде этого окна

- лезть в `web-permissions.json` и добавлять туда инструмент — он там уже есть;
- менять `defaultMode`;
- пересобирать снапшот окружения;
- искать ошибку в путях.

Всё это уже пройдено, по одному разу каждое, и ни одно не помогло. Окно на
`Execute SQL` — ожидаемое поведение.

## История разбора, чтобы не ходить по кругу

Проблема «окна возвращаются каждую сессию» решалась в четыре захода, и первые три были
неверными диагнозами. Оставлено намеренно: каждый выглядел убедительно.

| версия | почему оказалась неверной |
|---|---|
| Список не применяется, потому что его нет в `main` | Был. Проверка шла по устаревшему `origin/main` |
| Нужны копии `.claude/settings.json` по репозиториям | В веб-сессии не читаются: корень сессии `/home/user`, а он не репозиторий. В SellerBase копия лежала и не работала |
| Достаточно починить путь на `$HOME` | Необходимо, но мало: режим `acceptEdits` пропускает только правки файлов |
| Режим `dontAsk` | Такого значения не существует. Допустимы `plan`, `ask`, `auto`, `bypassPermissions` |

**Что в итоге оказалось нужно одновременно:** путь `$HOME/.claude/settings.json`,
`defaultMode: auto`, модель 4.6 или новее, и пересборка снапшота окружения после каждой
правки скрипта.
